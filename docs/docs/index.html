THE REFERENCE

Documentation

Set up Gyrus and bring useful context into your next coding session.

Install

You need a running local model server or an API key for a supported cloud provider. The installer handles Python through uv.

macOS / Linux

Terminal 
curl -fsSL https://gyrus.sh/install | bash
Read the installer ↗

Windows

PowerShell · Git required 
git clone https://github.com/prismindanalytics/gyrus.git
cd gyrus
.\install.ps1
Read the installer ↗

The setup wizard walks through your storage location, model choices, optional private Git sync, and an ingestion schedule. It also installs context instructions for detected tools.

After setup, run gyrus doctor to check the installation, then gyrus to process eligible session history. The first run may take longer while it works through existing sessions.

Scheduling and a second machine

The installer offers cron on macOS and Linux, or a Scheduled Task on Windows. Use gyrus log to see recent runs. Reopen setup with gyrus init when you want to change the setup options.

Git sync is optional. To connect another machine to an existing knowledge base after installing Gyrus, replace this example with your private repository URL: 

gyrus init --clone https://github.com/you/gyrus-knowledge

Daily workflow

Gyrus extracts notes from supported local session histories and uses them to update a compact handoff card for each project. Start a new session with the card for the repository you are working in:

From your project directory 
gyrus context --cwd "$PWD" --tool codex

gyrus context reads local files. It does not call a model or pull from GitHub. With a caller other than claude-code, it can also include Claude Code’s native memory for that directory.

Read the freshness line first. It reports when the card was built, what notes it covers, and known pending work or summary failures. Run normal ingestion when the card needs updating.

Supported session sources

Gyrus has adapters for these tools’ local session histories. Availability depends on the files each tool writes on your machine.

  • Claude Code
  • Codex
  • Claude Cowork
  • Cursor
  • Antigravity
  • GitHub Copilot
  • Cline
  • Continue.dev
  • Aider
  • OpenCode

It also imports supported Claude Code auto-memory files when they change. Exclude an adapter with excluded_tools in your config; use claude-memory to exclude that memory import. See the source path reference for default locations.

How cards stay compact

A rebuild uses the previous card, new project notes, and a bounded selection of recent notes. Fixed section limits keep the result small. A backlog may need several passes; work that does not fit remains pending.

When summarization fails, Gyrus can preserve the previous card with unsummarized notes as a fallback. Those notes stay pending for a later successful pass. A fresh build time alone does not mean the new work has been summarized.

Models & settings

Gyrus has two model roles: extraction turns session text into notes; card writing turns notes into project handoffs. Choose both with gyrus models, or edit ~/.gyrus/config.json.

Use models on your machine

Run an OpenAI-compatible model server, such as Ollama, LM Studio, or llama.cpp. Install the model you want on that server, then configure both roles. Replace your-installed-model with the exact model tag: 

{
  "extract_model": "local:your-installed-model",
  "merge_model": "local:your-installed-model",
  "local_base_url": "http://localhost:11434/v1"
}

The example endpoint is Ollama’s default. Set local_base_url to your server’s loopback URL. Keep the server running when scheduled ingestion runs.

Use a cloud provider

Gyrus supports Anthropic, OpenAI, and Google model providers. gyrus models shows the choices available to your installed version. Put provider credentials in ~/.gyrus/.env, using ANTHROPIC_API_KEY, OPENAI_API_KEY, or GEMINI_API_KEY.

You can mix local and cloud roles. Any role using a cloud provider sends the text it processes to that provider. Keep secrets out of config.json, which is included when Git sync is enabled.

Useful settings

Setting What it controls
excluded_tools Adapter keys to skip during ingestion. Defaults to an empty list.
repo_groups Map repository folder names to a shared project name.
ideas_mode "merge" updates the ideas page with a model. "append" archives incoming idea notes verbatim.
cards.max_per_run Maximum project cards rebuilt in a run. Default: 12.
cards.max_calls_per_run Model-call budget for card writing per run. Default: 60.
enable_personal_profile Opt in to personal and work-style notes in me.md. Default: false.

cards settings live inside a nested "cards": { … } object. For all settings, see the configuration reference.

Command reference

Run gyrus help for the full set of options in your installed version.

Command Purpose
gyrus Process eligible sessions and pending notes, then update the knowledge base.
gyrus context --cwd PATH Read a project handoff. Add --tool codex or the calling tool’s name.
gyrus doctor Report storage, schedule, model, sync, and ingestion health.
gyrus doctor --fix Run diagnostics and attempt supported automatic repairs. This can change local setup.
gyrus models Inspect or change extraction and card-writing models.
gyrus init Open the setup wizard.
gyrus sync Pull and push the configured Git remote.
gyrus log Read recent run history.
gyrus status Review and set project statuses.
gyrus merge Review suggested project-name consolidations. Accepted merges change stored project data.
gyrus compare Compare models using your sessions. Add --local-only to limit the comparison to local models.
gyrus update Update installed Gyrus code from GitHub.

--dry-run runs extraction without saving; it still sends eligible text to the configured model. --no-autosync skips automatic Git sync for that run. --base-dir PATH selects a different knowledge-base directory.

Files & history

Your knowledge base is accessible through ~/.gyrus/. The installer can link that path to the storage directory you choose. Markdown files open in any text editor.

projects/
One compact Markdown handoff card per project.
thoughts/
Extracted notes in dated JSONL files. These are extracted history, not copies of complete session transcripts.
status.md
A summary of project statuses.
ideas.md
Standalone ideas, with optional verbatim append mode.
projects.archive/
Older long-form project pages archived when they are converted to cards.
config.json / .env
Non-secret settings and separate provider credentials.

Keep your own notes

Add a ## Manual Notes section to a project card for text that must survive regeneration. That section is preserved verbatim; generated sections are rewritten when the card is rebuilt.

Keep ideas without rewriting the backlog

Set "ideas_mode": "append" to add incoming idea notes verbatim under Recent Idea Notes. This preserves the existing page and skips model-based idea merging. Extraction can still use a model. The archive grows over time and does not automatically consolidate ideas.

Privacy & cost

Gyrus is MIT-licensed software with no Gyrus subscription or hosted account. Cloud inference is billed by the provider you choose. Local inference uses your hardware and avoids provider inference charges.

What leaves your machine

  • Local models: use a server on your own machine for both extraction and card writing to keep model processing local.
  • Cloud models: relevant session text, extracted notes, and existing card content are sent to the configured provider as needed for that role.
  • Optional integrations: Git sync uploads knowledge-base files to your remote; Notion storage and email digests send their content to those services.

For a fully local workflow, use local models for both roles and leave external sync and integrations disabled. A remote server configured through GYRUS_LOCAL_BASE_URL is still a remote destination, even when its model name starts with local:.

Keep a synced knowledge-base repository private. Extracted notes may contain sensitive information. Credential redaction is enabled by default, but it is not a guarantee that all sensitive content is removed.

What to expect from summaries

Cards are historical reference, not instructions or a source of truth. Model-written summaries can omit details or retain old claims. Verify important facts against your repository and original evidence. The freshness line describes coverage and known failures, not correctness.

Troubleshooting

Start with gyrus doctor and gyrus log. Diagnostics report known issues; they cannot prove every summary is complete or correct.

No sessions are being found

Confirm that your tool writes a supported local history format, check the default source paths, and review excluded_tools in your config. A running session can also be deferred until it has been quiet long enough.

A local model is missing or unavailable

Start your model server, confirm that the configured model tag is installed, and check local_base_url. Use gyrus models to inspect both model roles. Check the server again from the environment that runs scheduled ingestion.

A card is stale or has unsummarized notes

Read the freshness line and recent run errors. Fix the model or configuration problem, then run gyrus again. Pending notes can take several passes within the configured budget. Put corrections that must persist in ## Manual Notes.

Doctor reports abandoned historical notes

Earlier failed merges may have left notes marked as skipped. Doctor makes that historical coverage gap visible; it does not automatically replay those notes. Review the affected projects before recovering old history, because it may describe work that has since changed.

Scheduled ingestion is not running

Check the schedule reported by doctor and the latest run history. The standard installer uses cron on macOS and Linux, or the GyrusIngestion Scheduled Task on Windows. Confirm that the scheduled process can access session files and reach the configured model server.

The same project has several names

Run gyrus merge to review potential aliases. Check the suggested groups before accepting them: similar names can belong to different projects. Use repo_groups when multiple repository folders intentionally share a project.

How does this work with native tool memory?

Each tool continues to use its own memory. Gyrus adds a handoff from supported session sources across tools. The context command can also pass Claude Code’s scoped memory to another calling tool when those files are available.
